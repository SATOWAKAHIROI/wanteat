# wanteat 要件定義書 v1.0

作成日: 2026-09-04

## 1. 背景・目的

### 1.1 背景

同棲中の家庭で夕食作りを担当しているが、**毎日の献立を考えること自体が負担**になっている。長く続けた結果レパートリーも枯渇気味で、同じメニューの反復に陥りつつある。

### 1.2 目的

「今日の夕食を何にするか」の意思決定を AI に委譲し、**献立決定から買い物までを1本の導線**にすることで、夕食担当の負荷を下げる。

### 1.3 解決する価値（優先順）

| 優先度 | 価値 | 実現手段 |
|---|---|---|
| 1 | **決断コストをゼロにする** | AI が1案だけを提示する。選択肢を並べない |
| 2 | **買い物をシームレスにする** | 確定した献立の材料を買い物リストへ自動展開 |
| 3 | **パートナーの希望を反映する** | リクエストを蓄積し、提案時に AI へ渡す |
| 4 | **マンネリを解消する** | 献立履歴を記録し、直近と重複しない提案をさせる |

**設計原則**: 「選ばせない」。比較・並列提示は決断疲れを再生産するため、UI 上で複数案を並べることは行わない。

---

## 2. スコープ

### 2.1 MVP に含めるもの

- ログイン認証（既存の JWT + HTTP-only Cookie 機構を流用）
- AI による夕食献立の提案（**主菜＋副菜** の2品）
- 提案のやり直し（上書きで新しい1案）
- 献立の確定と、材料・分量・手順の生成
- 買い物リスト（自動展開＋手動追加＋チェック）
- リクエストの登録と、提案への反映
- 献立履歴の記録と閲覧
- 好み設定（苦手食材・アレルギー・人数）

### 2.2 MVP で明確に作らないもの

意識的に外す。将来必要になった時点で改めて検討する。

| 除外するもの | 理由 |
|---|---|
| **冷蔵庫の在庫管理** | 入力の手間で運用が破綻するリスクが最も高い。買い物運用を「提案してから買う」に固定することで不要にした |
| パートナーのログイン | MVP は本人のみ。リクエストは本人が代理入力する |
| 料理の評価（また食べたい／微妙） | Phase2 |
| 週間まとめ提案 | 利用シーンを「毎日その場で」に固定したため不要 |
| 汁物・主食の提案 | 味噌汁・白米は固定運用のため提案対象外 |
| 朝食・昼食 | 夕食のみ |
| 栄養バランスの計算・可視化 | Phase2 以降 |
| 調理写真の記録 | Phase2 以降 |
| 複数案の並列提示 | 設計原則「選ばせない」に反するため恒久的に作らない |

## 3. 利用者

| 利用者 | MVP | Phase2 |
|---|---|---|
| **本人**（夕食担当） | ログインして全機能を利用 | 同左 |
| **パートナー** | ログインしない。リクエストは本人が代理で入力する | ログインしてリクエスト・評価を直接入力 |

**設計方針**: MVP はシングルユーザーとして実装するが、Phase2 でパートナーのログインに拡張できるよう、
`requests` テーブルに `requested_by`（本人／パートナー）カラムを最初から持たせる。
また全テーブルに `user_id` を持たせ、将来「世帯」概念を導入する際の移行余地を残す。

## 4. 主要シナリオ

### 4.1 メインシナリオ（毎日の利用）

1. 仕事帰りの電車内でスマホからアプリを開く
2. ホーム画面の「今日の献立を考えてもらう」ボタンを押す
3. **3〜5秒**で主菜＋副菜の1案が表示される（料理名・ひとこと説明・調理時間・主な材料）
4. ピンとこなければ「別の案」を押す。前の案は消え、新しい1案が表示される
5. 「これにする」を押す
6. 詳細な分量と手順が生成される（**15〜25秒**）。同時に買い物リストが作られる
7. スーパーで買い物リストを開き、カゴに入れながらチェックを付ける
8. 帰宅後、レシピ画面を見ながら調理する
9. 「作った」を押すと履歴に記録される

### 4.2 サブシナリオ

**条件を指定して提案させる**
「30分以内で」「豚こま肉を使い切りたい」「あっさりしたものがいい」といった条件を任意で入力してから提案を受ける。

**リクエストを登録する**
パートナーから「今度カレー食べたい」と言われた時に、その場でリクエストとして登録しておく。以降の提案時に AI へ渡され、適切なタイミングで献立に反映される。反映されたリクエストは自動でクローズされる。

**買い物リストに買い足しを追加する**
献立とは無関係な日用品や調味料を、買い物リストに手動で追加する。

## 5. 機能要件

### F1. 認証

既存の `AuthController` / `JwtAuthenticationFilter` をそのまま利用する。

- ログイン画面（実装済み `frontend/src/app/login/page.tsx` を流用）
- 未ログイン時は全画面からログイン画面へリダイレクト
- ユーザー登録 API は作らない。ユーザーは Flyway マイグレーションまたは手動 INSERT で作成する

**受け入れ条件**
- 未ログインで献立 API を叩くと 401 が返る
- ログイン後、Cookie が有効な間は再ログイン不要

### F2. 献立提案（第1段階）

AI が **主菜1品＋副菜1品** を提案する。

**入力（すべて任意）**
- 調理時間の上限（15分／30分／45分／指定なし）
- 使いたい食材（フリーテキスト）
- 気分・要望（フリーテキスト）

**AI へ渡すコンテキスト（自動）**
- 好み設定（苦手食材・アレルギー・人数・自由記述）
- 直近14日間に作った献立の料理名（重複回避のため）
- 未消化のリクエスト一覧
- 同一セッションで既に提示して却下された料理名（除外リスト）

**出力**
料理ごとに以下を返す。**この段階では分量と手順を生成しない**（応答速度のため）。
- 料理名
- ひとこと説明（20〜40字程度）
- 想定調理時間（分）
- 主な材料（3〜5個、分量なし）

**受け入れ条件**
- ボタン押下から表示まで、通常時 5秒以内
- 苦手食材・アレルギー食材が提案に含まれない
- 直近14日と同じ料理名が提案されない
- 生成中はローディング表示がされ、二重送信ができない

### F3. 別の案（再提案）

「別の案」を押すと、直前の案を**上書き**して新しい1案を表示する。

- 却下された料理名は除外リストに蓄積され、以降の提案から除かれる
- 却下履歴は画面遷移／リロードでリセットしてよい（サーバーに永続化しない）
- 第1段階の生成のみを繰り返すため、何度押しても高速かつ低コスト

**受け入れ条件**
- 連続して押しても同じ料理が再提示されない
- 前の案が画面に残らない（比較させない）

### F4. 献立の確定（第2段階）

「これにする」を押すと、提案内容を確定し、詳細情報を生成する。

**処理内容**
1. 献立レコードを作成（状態: 生成中）
2. AI に主菜・副菜それぞれの **材料・分量・手順** を生成させる
3. 分量は好み設定の人数に合わせる
4. 材料を買い物リストへ自動展開する
5. 反映されたリクエストがあればクローズする
6. 状態を「確定」に更新する

**受け入れ条件**
- 生成中であることが画面に分かる（進捗表示）
- 生成に失敗した場合は状態を「失敗」とし、再試行できる
- 同じ日付に確定済みの献立がある場合は、上書きするか別レコードにするかを利用者に確認する

### F5. 献立詳細（レシピ表示）

確定した献立の内容を表示する。キッチンで見ながら調理できる粒度。

- 主菜・副菜それぞれの料理名、調理時間
- 材料と分量の一覧
- 手順（番号付き）
- 「作った」ボタン（状態を調理済に更新）

**受け入れ条件**
- スマホ縦画面で手順がスクロールなしに追える程度の文字サイズ
- 材料と手順を切り替えずに同一画面で参照できる

### F6. 買い物リスト

**機能**
- 確定した献立の材料が自動で並ぶ
- チェックボックスで購入済みをマーク
- 手動でアイテムを追加・削除できる
- チェック済みを一括削除できる

**MVP での割り切り**
- 複数の料理に同じ食材が出ても**名寄せ・合算はしない**（「玉ねぎ 1/2個」が2行並ぶ）。名寄せは将来課題とする
- 家にある調味料等は利用者が手動でチェックを外す／削除する

**受け入れ条件**
- スーパーで片手操作できるタップ領域
- オフラインでも表示済みの内容は読める（将来課題。MVP では必須としない）

### F7. リクエスト

「食べたいもの」を蓄積し、提案時に AI へ渡す。

- 登録時に「本人／パートナー」を選択する
- 状態は「未消化」「消化済」の2つ
- 提案に反映されたら自動で消化済にする
- 手動での消化済／削除も可能

**受け入れ条件**
- 未消化のリクエストがある状態で提案すると、いずれ献立に反映される
- 反映された際に、どのリクエストが消化されたか利用者に分かる

### F8. 好み設定

- 世帯人数（分量計算に使用）
- アレルギー（提案から確実に除外）
- 苦手な食材
- 自由記述（「和食が多めがいい」等）

**受け入れ条件**
- アレルギー食材は提案・レシピのどちらにも一切出現しない
- 設定変更が次回の提案から反映される

### F9. 献立履歴

- 日付順の一覧（料理名とサムネイル代わりの区分表示）
- 詳細画面へ遷移できる
- 削除できる
- **提案時の重複回避に内部利用される**（直近14日）

### 7.2 提案中の状態について

第1段階の提案結果は **DB に永続化しない**。フロントエンドの state に保持し、「これにする」を押した時点でサーバーへ送る。
却下した料理名の除外リストも同様にフロントが保持し、再提案リクエストに含めて送る。

これによりサーバーはステートレスに保たれ、「上書きで新しい1案」という仕様に余計なテーブルが不要になる。

## 8. API 設計

既存の `/api/auth/**` に合わせ、`/api/` 配下に配置する。全て認証必須（`/api/auth/**` を除く）。

| メソッド | パス | 概要 |
|---|---|---|
| POST | `/api/menus/suggest` | **第1段階**。条件と除外リストを受け、主菜＋副菜の案を1件返す。DB 書き込みなし |
| POST | `/api/menus/confirm` | **第2段階**。提案内容を受けて確定。詳細生成・買い物リスト展開・リクエスト消化を行う |
| POST | `/api/menus` | 手動で献立を確定する（AI 不使用）。材料と手順をすべて指定する |
| GET | `/api/menus` | 履歴一覧。`from` / `to` クエリで期間指定 |
| GET | `/api/menus/{id}` | 献立詳細（料理・材料・手順） |
| PATCH | `/api/menus/{id}/cooked` | 調理済にする |
| DELETE | `/api/menus/{id}` | 削除 |
| GET | `/api/shopping-items` | 買い物リスト取得 |
| POST | `/api/shopping-items` | 手動追加 |
| PATCH | `/api/shopping-items/{id}` | チェック状態の更新 |
| DELETE | `/api/shopping-items/{id}` | 削除 |
| DELETE | `/api/shopping-items/checked` | チェック済みを一括削除 |
| GET | `/api/requests` | リクエスト一覧。`status` で絞り込み |
| POST | `/api/requests` | 追加 |
| PATCH | `/api/requests/{id}` | 消化済にする |
| DELETE | `/api/requests/{id}` | 削除 |
| GET | `/api/preferences` | 好み設定の取得 |
| PUT | `/api/preferences` | 好み設定の更新 |

**エラー形式**は既存の `GlobalExceptionHandler` の `ErrorResponse(status, message, errors)` を踏襲する。
AI 生成失敗時は新設の例外（例: `AiGenerationException`）を 502 にマッピングし、フロントで再試行導線を出す。

## 9. AI 連携設計

### 9.1 構成

**AI の呼び出しは必ずバックエンドから行う。** API キーをフロントエンドに露出させない。

```
ブラウザ → Next.js → Spring Boot (AiMenuService) → Claude API
```

### 9.2 2段階生成

| 段階 | タイミング | 生成内容 | 目標応答時間 |
|---|---|---|---|
| 第1段階 `SUGGEST` | 提案ボタン／別の案 | 料理名・説明・調理時間・主な材料 | **実測 約13秒** |
| 第2段階 `DETAIL` | 「これにする」 | 材料・分量・手順 | **実測 約19〜23秒** |

**採用理由**: 「上書きで再提案」を何度も押す前提のため、毎回フルレシピを生成すると待ち時間が決断体験を損なう。
軽い生成を繰り返し、確定した1件だけ詳細生成することで、体感速度と API コストの両方を最適化する。

### 9.3 プロンプトに渡すコンテキスト

**第1段階**
- 好み設定（人数・アレルギー・苦手食材・自由記述）
- 直近14日間に作った料理名の一覧
- 未消化のリクエスト一覧
- 利用者が指定した条件（調理時間・使いたい食材・気分）
- 同一セッションで却下された料理名

**第2段階**
- 確定した料理名と説明
- 世帯人数（分量のスケーリング）
- アレルギー・苦手食材（再度渡して確実に除外）

### 9.4 出力の構造化

料理名・材料・手順を確実にパースするため、**JSON スキーマを指定した構造化出力**（tool use）を用いる。
自由文をパースする実装は行わない。

### 9.5 失敗時の扱い

- タイムアウトは第1段階30秒／第2段階60秒
- 失敗時は自動で1回リトライ
- それでも失敗した場合、第1段階はエラー表示＋再試行ボタン、第2段階は献立を `FAILED` 状態にして再生成できるようにする

### 9.6 モデルとコスト

- 初期は速度重視で軽量モデルを試し、提案品質が不足する場合に上位モデルへ切り替える
- モデル名は環境変数で切り替え可能にする
- `ai_generations` テーブルのトークン数から実コストを把握し、後から判断する
- 想定利用量は 1日あたり第1段階 数回＋第2段階1回程度

### 9.7 環境変数

`compose.yaml` の backend サービスに以下を追加する。

| 変数 | 用途 |
|---|---|
| `ANTHROPIC_API_KEY` | Claude API キー。**リポジトリにコミットしない**。`.env` から読み込む |
| `AI_MODEL` | 使用モデル名 |

`.env` は `.gitignore` に追加し、`.env.example` をコミットする。

## 10. 非機能要件

| 項目 | 要件 |
|---|---|
| **対応端末** | スマートフォン（縦画面）を第一とする。PC は最低限表示できればよい |
| **利用環境** | 電車内（通信が不安定）とスーパー店内での利用を想定 |
| **応答性** | 第1段階は実測 約13秒、第2段階は約19〜23秒。**当初目標の「第1段階5秒以内」は達成できなかった**（構造化出力と `effort` が併用できないため）。待ち時間が長いので、**生成中の進捗表示は必須**とする |
| **可用性** | 個人利用のため停止を許容。SLA は定めない |
| **セキュリティ** | API キーはバックエンドのみ。既存の JWT + HTTP-only Cookie 認証を維持。CORS は既定のオリジンのみ許可 |
| **コスト** | AI の API 利用料は月数百円以内に収める |
| **デプロイ** | 当面はローカルの Docker Compose で運用。外出先から使うため、後日 VPS 等へのデプロイを検討する（下記「未決事項」参照） |
| **バックアップ** | MySQL のボリュームを定期バックアップ。方式は未定 |

## 11. 未決事項

| # | 論点 | 備考 |
|---|---|---|
| 1 | **デプロイ先** | 「電車内で使う」ため外部からアクセスできる必要がある。ローカル Docker のままでは要件を満たさない。VPS / Fly.io / Cloud Run 等の選定が必要 |
| 2 | HTTPS 化と Cookie 設定 | 外部公開時は `secure(true)` と `SameSite` の見直しが必須 |
| 3 | 使用モデルの選定 | 実際の提案品質を見て決める |
| 4 | 手順の保存形式 | JSON 配列で始めるが、将来ステップ単位の操作が必要になれば正規化する |
| 5 | 買い物リストの食材名寄せ | MVP では行わない。運用してみて不便なら実装する |
| 6 | 日付の扱い | 深夜0時をまたいで操作した場合、どの日の献立として記録するか |
| 7 | 分量のスケーリング精度 | AI 任せにするか、2人分固定で生成するか |

## 13. 開発ステップ（提案）

| Step | 内容 | 完了の目安 |

| 0 | **土台の整理**。`Sample*` 一式を削除し、起動失敗を解消する | `docker compose up` で backend が正常起動する |
| 1 | **DB スキーマ**。`V2__menu_planner.sql` とエンティティ・リポジトリを作成 | テストが通り、アプリが起動する |
| 2 | **好み設定**（F8）。API と設定画面 | 好みを保存・取得できる |
| 3 | **AI 提案 第1段階**（F2・F3）。`AiMenuService` とホーム画面 | ボタンを押すと主菜＋副菜の案が出る／別の案が出せる |
| 4 | **献立確定 第2段階**（F4・F5）。詳細生成と献立詳細画面 | レシピが表示され履歴に残る |
